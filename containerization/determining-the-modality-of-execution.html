Determining the modality of execution

Before starting with containerization, it is important to clearly determine the modality of execution of the software that you intend to containerize. You can do so by asking yourself and answering questions such as:

  • What dependencies and environment does the software require during its execution?

  • When should the software start?

  • When should the software stop?

  • What services does the software need to access during its execution? For each service consider the following questions:

    • Can the service be run as a separate container deployed on the same IIASA Kubernetes cluster? (preferred if possible because it allows much benefit to be derived from the orchestration functionality provided by Kubernetes).

    • Is the service available only remotely via the Internet?

    • If neither of the above, is there really no other option than deploying the service in the same container? (a last resort).

  • What service does the software provide during its execution?

  • Should the software execute as a job?

    • Taking in inputs at the start and producing outputs at the end.

    • For example, a model scenario run.

  • Does the software need to run continuously?

    • For example, because it provides an on-demand service.

  • What inputs from outside the container does the software process?

  • What output should the software deliver outside of the container?

  • Can or do parts of the software execute in parallel?

    • If so, can these be put in separate containers?

  • Can multiple copies of the software execute in parallel?

    • Can these be run as multiple container instances?

The answers to these questions will obviously constrain how the container images have to be built, what interfaces should be defined, what file and network resources should be provided, and how the running of the containers is to be orchestrated.

Strive for single-purpose containers

While finding answers to the above questions, aim to limit the software installed in a container to a single purpose. Doing so allows the resulting containers to be deployed and managed with clarity.

Having a container serve a single purpose does not guarantee simplicity. For example, when the purpose of the container is to provide a full-featured scientific software stack to a researcher, quite a few software components may need to be included. In such a complex case, you will need to decide on how the software components included in the container will be managed.

Process management

The containerfile (typically a Dockerfile) among others specifies what software to run when the container starts (for a Dockerfile via CMD or ENTRYPOINT). However, the software that you installed in the container may require you to start multiple collaborating processes that run in parallel for the container to serve its purpose. These processes will need to be managed. In such a circumstance, you need to run an init system or process manager when the container starts. How processes are managed is specified in the configuration of the chosen manager.

The default init system of most Linux distributions is systemd but it has sprawling functionality that is overkill for the purposes of most containers. Container images on which you may wish to base your container therefore typically do not include systemd and only occasionally use some other init system or process manager. You may therefore have to pick and install a manager that fits your purpose. Below, some options are listed.

  • Tini (tinier init):

    • A lightweight init system designed specifically for Docker containers to help with proper handling of signals and reaping zombie processes.

    • It is often used in simple container setups where resource usage needs to be minimal.

  • Supervisord:

    • An application monitor and process control tool that can automatically restart failed services, manage logs, and handle process communication.

    • It’s popular for its robustness and logging capabilities, making it suitable for more complex container environments.

  • s6:

    • A supervisory process control system that is highly configurable with a strong focus on service dependencies and inter-service communication.

    • It offers advanced features like dependency handling, which makes it ideal for containers running multiple services where precise orchestration is necessary.

    • s6-overlay allows you to easily add s6 on top of existing containers.

  • Runit:

    • Runit provides a simple init system that uses very little memory while offering advanced service management capabilities such as runlevel support and dependency tracking.

    • It’s well-suited to environments requiring reliability and minimal overhead but more features than Tini.

  • OpenRC:

    • An init system similar in philosophy to sysvinit, providing compatibility with traditional UNIX-style service scripts.

    • While not as commonly used within containers due to its larger footprint compared to alternatives like Tini or runit, it’s still a viable option for complex services that benefit from detailed control and scripting.
